# 2026-10-05 Buddy 专用模式签到失效排查（只读诊断，未改代码）

## 最终结论（10:38 复测后定稿）：10001 语义没变，变的是「服务端故障复用了同一个 code」

### 直接原因（本项目可修）
`executors/buddy.py:301-321 _do_claim()`（同源逻辑在 `D:\.Buddy\Buddy-signin\buddy_checkin.py:556`）：
```python
st, body = self._call(ENDPOINT_CHECKIN, token, uid, domain)
...
if code == 10001 or "已签到" in msg:
    return 'already', [], data      # → success=True, message="今日已签到"
```
**它只看响应体里的 code，完全不看 HTTP 状态码，也不校验 msg。**

服务端两种返回的 code 完全相同（都是 10001）：

| 场景 | HTTP | body |
|---|---|---|
| 正常「今天已签到」 | **400** | `{"code":10001,"msg":"今天已签到，请明天再来"}` |
| 服务端故障（近期新增分支） | **500**（响应头 `X-APISIX-Upstream-Status: 500`） | `{"code":10001,"msg":"签到配置加载失败，请稍后重试"}` |

→ 500 故障被当成「已签到」→ 写回 success=1 → already 分支直接 break、不重试 → 当天彻底漏签。

### 实测时间线（同一天内服务端间歇性故障，已证实）
- 10:18~10:21 → 全部 **500「签到配置加载失败」**（4 个域名 × 多路径均如此）
- 10:38~10:40 → 恢复正常：**400「今天已签到，请明天再来」**，连续 6 次探测（15s 间隔）稳定
- 活动状态接口同时恢复：`active=true, today_checked_in=true, streak_days=6,
  checkin_dates=[10-05,10-04,10-03,10-02,10-01,09-30], season=10, total_credits=600,
  theme_name="Buddy加油站", start_time 2026-09-30, end_time 2026-10-15`

⇒ 故障不是「活动下线」，是服务端**间歇性的签到配置加载失败**；NAS 定时点在 08:05/08:06，
正好落在故障窗口内（10-04 08:06 失败、09:45 恢复；10-05 08:06 失败、10:18 仍失败、10:38 恢复）。

### 排查中排除的干扰项
- 路径未变：`/v2/billing/meter/daily-checkin` 与 `/checkin-activity-status`，带不带 `/v2`、四个域名
  （www.workbuddy.cn / copilot.tencent.com / wb.tencentbuddy.com / www.codebuddy.cn）行为完全一致。
- 令牌正常：NAS token_store 用本机 `data/encryption.key` 可解密，access_token 有效至 2026-11-12。
- **不是**图灵盾设备令牌导致：补 `X-Device-Token`（真值/假值）返回不变。
- 老接口 `/billing/meter/checkin-status` 恒返回 `active=false, today_checked_in=false, ..., activity_name=""`
  —— 这是该接口自身已废弃/被降级（桌面端早已改用 `checkin-activity-status`），**不代表活动下线**，别拿它当判据。

### NAS 日志与实测的对应关系（Buddy 站点 id=28）

## 附带的潜在风险（非本次主因，后续要处理）
1. 本项目 `_do_claim` 忽略 HTTP 状态码 —— 这正是本次事故的机制，必须修。
2. 客户端签到请求现在带 `X-Device-Token`（TURING_SHIELD_ID_HEADER，图灵盾设备令牌），
   并对 `/billing/meter/(daily-checkin|checkin-activity-status)$` 做专门风控日志（app.asar offset 138100284）。
   当前不影响（加不加头响应一致），但服务端随时可能收紧。
3. 客户端 `mapCheckinStatus`（app.asar offset 137858110）映射的是 **1001/1002/1003**，
   与本项目使用的 10001 不是同一套码 —— 说明客户端还走着一套旧接口分支，留作观察。
4. 本机登录态 `AppData\Local\CodeBuddyExtension\Data\Public\auth\workbuddy-desktop.info`
   已改为加密信封（`{"$wbEncrypted":1,"envelope":"..."}`），buddy.py 的
   `auth.get("accessToken")` 回退路径会拿到 dict 而崩溃（D:\.Buddy 项目已用 buddy_auth.py 解决，本项目未同步）。

## 修复方向（用户要求先不动代码，待确认后再改）
1. **判定加 HTTP 状态码**：`code==0` 且 2xx 才算成功；`code==10001` **只有 HTTP 400 且 msg 含「已签到」**才算已签；
   其余（含 500）一律判失败。
2. **让失败可重试**：当前 `already` 分支直接 break，且重试间隔仅 3 秒 —— 跨不过长达 1~2 小时的故障窗口。
   建议失败后台按间隔重试（如 30 分钟后补签一次），而不是当天直接跳过。
3. 可选：签到前查 `checkin-activity-status`，`active=false` 时明确提示「活动未开启」。

## 排查手法（可复用）
1. 扫描 `C:\Program Files\WorkBuddy\resources\app.asar`（317MB，明文含全部接口定义）找接口路径/状态码/请求头；
2. NAS 导出的 auto_sign.db 可用本机 `data/encryption.key` 解密 token_store（两端密钥相同），
   拿到 access_token 后直接复现请求；**不要调 refresh**（会轮换 refresh_token 影响 NAS 端）；
3. 多域名 × 多路径（带/不带 /v2）对照探测，能快速区分「路径迁移」与「服务端故障」；
4. **同一接口要在不同时间点重复探测** —— 本次就是靠 10:18（500）与 10:38（400）两次对照才定性的，
   单次探测会得出错误结论。
   临时脚本放在 `_tools/`（临时目录前缀约定），含明文令牌的 `_tools/_nas_token.json` 用完即删。

# 2026-10-05 修复落地（已改代码）

## 1) `executors/buddy.py::_do_claim` —— 判定改为 HTTP 状态码优先
顺序：5xx → 一律 fail（服务端故障会复用 code=10001，只有状态码能区分）；
2xx 且 code==0 → success；code==10001 且 msg 含「已签到」→ already（正常为 HTTP 400）；
其余（未知 code / 401 / 其它 4xx）→ fail。失败信息里带上 HTTP 状态码便于排查。

## 2) `executors/buddy.py::run` —— 签到专属重试
新增模块常量 `CHECKIN_RETRY_TIMES = 3`、`CHECKIN_RETRY_INTERVAL = 10`。
重试循环**只包裹签到调用**；叠加 `sign_service` 的整体重试（retry_times，当前 2）后
最多 2×3=6 次。每日对话在签到成功后单独执行一次，不参与重试（避免发 3 次对话）。

## 3) 清除本机登录态读取
删除 `DEFAULT_AUTH_REL_PATH`、`_resolve_auth_file()`、`auth_file_cfg` 及 `import os`；
`_load_token()` 现在只认站点 `token_store`（用户在 WEB 管理页「令牌」框提交）。
同步更新了 `templates/add_edit.html` 中 Buddy 令牌框的说明文案。

## 验证方式（离线，不联网）

覆盖 7 组判定矩阵 + 「3 次 500 判失败」+「前 2 次失败第 3 次成功且只发 1 次对话」+「无令牌不回退登录态」，全部通过。

# 2026-10-05 第二轮修改：对话与签到解耦（用户澄清需求）

**用户明确**：签到与对话是两个不同功能与需求。对话每天**成功发起一次**即可，
重复发起会浪费积分；成功 = 发出提问且收到含「好」的回复；「不管什么情况下」每天只成功发起一次。

## 改动（`executors/buddy.py`）
1. `run()` 重构：抽出 `_claim_with_retry()`（签到 + 自身 3 次重试）；
   **对话移到签到判定之外**，签到成功或失败都会执行一次。
   签到失败时也构造并返回 appendix（新增「签到：失败（原因）」行），不再丢失状态块。
2. `_run_chat_once()`：删除 `and not self.ctx.is_manual` 例外 ——
   **手动执行也遵守「当日已成功则跳过」**（原设计为便于测试，会重复发对话浪费积分）。
3. `_do_chat()` / `_chat_completions()`：成功判定从「HTTP 200 即成功」改为
   **回复文本必须含「好」**（`_reply_has_ok`）；ACP 回复无效则回退 chat/completions 再判。
4. `_extract_acp_text()` **修掉一个既有隐患**：原实现 `p.encode().decode('unicode_escape')`
   在服务端直传 UTF-8 中文时会把字节按 latin-1 还原成乱码，
   导致新加的「回复含好」判定永远失败。改为含 `\` 时交 `json.loads` 反转义，否则原样保留。

失败语义：**当日未成功则允许再试**（整体重试会再次进入对话）；当日成功一次后永久跳过。
