# 2026-11-12 躺平站点（tangpt.top）Cloudflare Turnstile 配置

## 抓包事实
- 登录：POST /takelogin.php，表单字段 `username` / `secret` / `two_step_code` / `cf-turnstile-response` / `response`（密码不在表单里，由页面 JS 算 sha256(clientHash, challenge secret) 后写入 hidden `response`）。
- 签到：POST /attendance.php，body 仅 `cf-turnstile-response`。
- 两处都要 Turnstile token，**API 模式无法实现**（token 由浏览器 JS 生成，一次性、约 5 分钟有效）。
- 站内登录页 turnstile 为 managed（不可见），实测约 14 秒自动生成 token。

## 修复的两个真实缺陷（executors/browser.py）
1. `detect_login_fields` 的 `cssOf` 兜底返回裸 `tagName`。该站密码框无 name/id/placeholder，导致密码选择器变成 `input`，会把密码填进第一个 hidden 字段 → 登录必失败。
   改为在 placeholder 之后加 `[type="xxx"]` 兜底，现在返回 `input[type="password"]`。
2. `is_login_page` / `_has_turnstile` / `_handle_turnstile` / `_wait_cloudflare` 用 `page.ele('input[name="cf-turnstile-response"]')` —— DrissionPage 4 不认这种纯 CSS 写法，永远取不到值，Turnstile 只能干等超时后"宽松放行"。
   新增 `_turnstile_token_len(driver)` 统一走 JS 读取，token 就绪立即返回（实测从等 30 秒降到约 14 秒）。
3. `click_sign_button` 自定义选择器补充 JS（querySelector）回退，支持 `input[value="立即签到"]` 这类标准 CSS；JS 兜底从只找 `.x-button` 扩展为 `.x-button, button, input[type=submit], input[type=button], a`，按文案"立即签到"精确定位。

## 该站正确配置
- 模式：浏览器模式
- 登录地址 https://www.tangpt.top/login.php，签到地址 https://www.tangpt.top/attendance.php
- **必须勾选「Cloudflare 验证」**（否则 turnstile 完全不处理）
- 建议勾选「登录优先」（先登录再进签到页）
- 签到按钮选择器可留空（JS 兜底能定位「立即签到」），或填 `input[value="立即签到"]`
- 全局 `cf_timeout` 需 ≥ 30 秒（token 生成约 14 秒）
- 数据库 id=14，原 has_cloudflare=0/login_first=0，是失效主因

用库中真实凭据端到端跑通：turnstile 通过 → 登录成功（跳 index.php）→ 打开签到页 → 识别已签到。今日已签到，"

## 复核：纯 API 模式是否可行（结论：不可行，已实测）
### 抓包归类
- 242 / 255：`POST /cdn-cgi/rum` → Cloudflare **RUM 性能上报**（LCP/CLS/TTFB），与验证无关。
- 287：`GET hagen.challenges.cloudflare.com/cdn-cgi/challenge-platform/h/g/i/...` → Turnstile 内部挑战令牌交换，
  响应头 `cf-chl-peek`。这条是真正的 CF 验证链路。
- 265：`challenges.cloudflare.com/.../turnstile/f/av0/rch/f69id/0x4AAAAAAF5fQl5oXZLNyNtX/auto/fbE/new/flexible`
  → Turnstile 组件 iframe 外壳（rch = 重新渲染挑战）。
- 254：`GET attendance.php`（未签到态）→ 签到表单只有 `<div class="cf-turnstile" data-sitekey="0x4AAAAAAF5fQl5oXZLNyNtX">`
  + `<input type="submit" value="立即签到">`，**没有 formhash、没有其它隐藏字段**。
- 219：`POST takelogin.php` 302 成功；299：`POST attendance.php` 200 签到成功（第 279 次/连续 107 天）。

### 登录签名（纯 Python 可复现，已验证算法）
`POST /api/challenge {"username":u}` → `data.{secret,challenge}`
`response = HMAC_SHA256(key=challenge, msg=SHA256(secret + SHA256(password)))`
表单提交 `username / secret(空) / two_step_code / response / cf-turnstile-response`。密码框无 name，只走哈希。

### 决定性实测（本次用库内真实凭据）
- 不带 token 登录 → 200 页面提示 `Captcha verification token is missing.`
- 仅用 `c_secure_pass` cookie（有效期 1 年）GET attendance.php → 200 正常（不依赖 cf_clearance）
- `POST attendance.php` 不带 token → `Captcha verification token is missing.`
- `POST attendance.php` 带伪造 token → `Captcha verification failed.`（服务端 siteverify 真校验）

→ 结论：登录与签到**都**强制 Turnstile，token 由 Cloudflare 签发、单次有效，纯 requests 无法生成。
  **纯 API 模式对该站不可行**，api / browser_api 两种模式均无效；只能浏览器模式。
  唯一理论替代是第三方 Turnstile 打码平台，但成功率不稳、付费且违规，不建议。

### 附带事实
- `c_secure_pass` 有效期 1 年（expires=1825999594）。项目 browser.py 会注入站点 cookies（L858-871）并在登录后回写，
  故首次登录后后续运行可跳过登录环节，只剩签到页一次 turnstile（约 14 秒）。
- 站点 id=14 数据库 cookies 列已存 c_secure_pass（加密存储，明文搜不到属正常）。


## 桌面浏览器模式(CDP)：本地 Windows + NAS 双环境适配

背景：容器内无头 Chromium 过不了 Cloudflare 托管挑战，HDTIME / 家园两站在浏览器模式下失败。
按 `D://.Buddy//InstaBox//CDP远程浏览器接入说明.md` 落地 `mode='desktop'`，一个模式覆盖两种运行环境。

### 地址解析（executors/browser.py: resolve_desktop_address）
- 设置页 `desktop_browser_address` 显式配置优先：`host:port` 连远端；`local` 强制本地拉起；空/auto 走自动。
- 自动：Windows 先拉起本地 Chrome/Edge（固定 profile `chrome_data/desktop`、端口 9333）；
  非 Windows 依次探测 `172.20.0.1:9222`（zljiscx 容器宿主）→ `100.100.1.10:9222`（组网固定入口）→ `127.0.0.1:9222`。
- 显式地址不可达直接报错，不静默换浏览器（避免在 NAS 上误用容器内无头 Chromium）。

### 关键实现点
- `DrissionPageDriver(headless=False, address=...)` 远程分支：不建临时目录、不启本地进程；先 `ensure_page_tab` 再连。
- `close()` 远程分支：先 `PUT /json/new` 补一个空白标签，再 `GET /json/close/<tab_id>` 关自己的；**绝不 quit**。
  实测（Chrome 157）关掉最后一个标签会让浏览器进程直接退出，故必须“先补后关”。
- `open()` 增加 CF interstitial 退避重载（`cf_retry`=3 / `cf_backoff`=5，可用 config 覆盖），
  只认 `Just a moment` / `cf_chl_opt` 等强特征，内嵌 Turnstile 的正常页面不会误重载。
- `set_cookies` 剔除控制字符、给 `cf_*` / `__cf*` 强制站点域名（家园站点里有重复 cookie，实测 10/10 设置成功）。
- `_ensure_no_proxy` 把 CDP 主机写进 NO_PROXY，避免全局代理让 requests / DrissionPage 连不上。
- `DesktopBrowserExecutor` 强制 `has_cloudflare=1`、`min_cf_timeout=60`：该模式就是给 CF 站点的，无需再勾选。
- 执行器挂点 `_make_driver(headless)`，`run()` / `login_and_refresh_cookies()` 都走它，只覆写一处即完成复用。

### 实测（本机 Windows，Chrome 157）
- 本地自动拉起 → 连接 → 打开页面 → 读写 cookie → 关标签 → 浏览器存活 → 二次复用同一实例：全部通过。
- 端到端 desktop 模式：躺平 / HDTIME / 家园 三站均 success（走库内 cookie，签到页未被 CF 拦截）。
- 分支：显式地址可达 / 不可达 / `http://` 前缀容错 / 不可达时返回「桌面浏览器不可用」而非抛异常，全部符合预期。
- 模拟 NAS（os.name='posix'）：候选探测命中与全部不可达两种分支均正确。

### 使用与注意
- NAS：设置页「桌面浏览器地址」填 `100.100.1.10:9222`（或容器在 zljiscx 时留空即可命中 172.20.0.1）。
- Windows：留空即自动拉起本地 Chrome；可用「桌面浏览器路径」指定非标准安装位置。
- 并发互斥：zljiscx 容器自身的 auto-signin 也用同一个浏览器，两边不能同时跑这两个站点。
- 不要拿 desktop 模式拿到的 cookie 回 NAS 用 api 模式重放（出口 IP 不同，cf_clearance 会失效）。
