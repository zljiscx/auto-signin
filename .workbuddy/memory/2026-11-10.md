# 2026-11-10 hxpt.org 抓包分析与模式判定

## 结论
`api` 模式可配该站自动签到，无需浏览器；已用项目 ApiExecutor 端到端跑通（登录 → 签到）。

## 抓包事实（Reqable ID 363 登录 / 494 签到）
- 登录：`POST https://www.hxpt.org/api/v1/auth/login`，JSON `{"username","password","remember":true}`
  → `{"code":0,"data":{"token":"JWT..."}}` + `Set-Cookie: flux_token=...; HttpOnly; SameSite=Lax; Secure`
  登录**不校验 CSRF**（实测无 flux_csrf cookie、无 x-csrf-token 头也能 code=0）。
- 签到：`POST https://www.hxpt.org/api/v1/attendance/checkin`，body `{}`
  → 首次 `{"code":0,"data":{"base":8,"gacha_ticket":true,"reward":8,"streak":1,...}}`
  → 重复 `HTTP 400 {"code":1002,"message":"参数校验失败: 今天已经签到过啦"}`
- 状态查询：`GET /api/v1/attendance` → `{"code":0,"data":{"checked_today":true,"makeup_cards":10,...}}`，仅 token 即可。

## 关键机制：CSRF 双提交（签到强制）
- 签到头 `x-csrf-token` 必须与 cookie `flux_csrf` **值相同**，否则 `HTTP 403 {"code":2003,"message":"无权限"}`。
- 实测只比较两者是否相等，**不校验值本身**：填任意值 `deadbeef` 也能进入业务逻辑。
- 站点不下发 `flux_csrf`（`/`、`/torrents`、`/login` 均无 Set-Cookie），因此需自行伪造一对同值。
- 不需要 `c_secure_pass`、`flux.session`、`SITE_TOTAL_ID`、`_qimei_*`，仅 `flux_token` + 双提交即可。

## 落库配置要点（api 模式）
- login.steps：登录 POST，body 用 `{{username}}`/`{{password}}`，`success_rule` 判 `$.code == 0`。
- 签到 steps.headers 写死：
  `"x-csrf-token": "{{csrf}}"`，`"Cookie": "flux_token={{cookie:flux_token}}; flux_csrf={{csrf}}"`
  csrf 取 `variables` 里的静态值；显式 Cookie 头优先于 session jar（requests 只在无 Cookie 头时才从 jar 生成）。
- success_rule 建议 `{"contains":["\"code\":0","今天已经签到过啦"]}`：api 执行器无「已签到」状态，只判成功/失败，否则每个已签到日都会误报失败。
- 顶层 `use_site_cookies` 设 false，避免与手写 Cookie 头拼接冲突。

## 复用经验
- 判断某站能否走 api 模式，先看三件事：登录是否需要 CSRF、签到是否强校验 CSRF/指纹、鉴权 cookie 能否由程序获得（服务端签发的 HMAC 类 cookie 不行）。
- `render_vars` 支持 `{{cookie:名称}}`，`extract_value` 支持 `json:`/`cookie:`/`header:`/`regex:`，足够拼多步登录链。

## 修复：API 模式看不到账号密码输入框
现象：`api` 模式需要 `{{username}}`/`{{password}}` 变量，但界面上没有输入处。
原因：用户名/密码两个 input 原本写在 `<div id="secBrowser">` 里，`switchMode()` 对 `api` 模式整体隐藏该区块。
后端本就按非 buddy 模式一律保存 `username`/`password`（`_collect_site_form` + `SignContext`），纯前端可见性问题。
改法：抽出独立区块 `#secAccount`（放在 `#secUrlRow` 之后），`api`/`browser`/`browser_api` 显示，`buddy` 隐藏
（含内联 `style="display:none"` 防止加载闪动）；`switchMode()` 增加一行 toggle。`#secBrowser` 只保留登录优先/验证码/CF/选择器。

## hxpt.org 登录报 SSL CERTIFICATE_VERIFY_FAILED（NAS 容器）
现象：`[SSL: CERTIFICATE_VERIFY_FAILED] unable to get local issuer certificate (_ssl.c:1006)`，发生在登录步骤请求阶段。
根因：`https://www.hxpt.org` 证书链为 leaf ← Google Trust Services WE1 ← GTS Root R4（由 GlobalSign Root CA 交叉签名）。
本机 venv 的 certifi(2026-08) 校验通过；容器内 `requests` 走的是自带 certifi，与系统 CA 库(`/etc/ssl/certs`)不是一套。
`buddy.py` 用 `ssl.create_default_context()`（系统库）所以正常 —— 说明容器系统 CA 可用，问题在 certifi 侧缺失/过旧。
解决：短期站点级 `"verify_ssl": false`（登录步骤会继承顶层）；根治容器内 `pip install -U certifi` 或 `REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt`。
代码：`executors/api.py` 新增 `_ssl_hint(err)`，登录失败与签到步骤异常时追加可操作提示（仅命中 CERTIFICATE_VERIFY_FAILED 时）。
